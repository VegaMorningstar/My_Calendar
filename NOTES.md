# Project notes: My Calendar

One file for how we work here and what is still undecided. It is the single source of truth: `CLAUDE.md` just imports it, and the README only describes what the app does. **Keep it up to date**: when a rule changes or an item is settled, change it here in the same commit.

A photo calendar built around one reusable element, `src/photo-calendar/`. See `README.md` for what it does and how to run it.

## Ground rules

### How we work

- **Commits and pull requests carry no mention of Claude or Anthropic**: no `Co-Authored-By` trailer, no "Generated with" line, no AI author. Strict, in every commit, and it overrides any default.
- **No em dashes anywhere** (code, comments, docs, commit messages). Use a comma, colon, parentheses or a plain hyphen.
- **Show UI changes on localhost** (`http://127.0.0.1:5173`) before pushing when asked, with `?lq=0` to compare against the plain boxes if useful.
- **Push only when told to.** Never run commands that change git history or push otherwise. Pushes use the `github-personal` SSH host (the VegaMorningstar account); do not use other keys. Pushing to `main` deploys to GitHub Pages, which is what the owner tests on their phone.
- **"Think only", "brainstorm" or "investigate first" means no code changes.** Discuss, then build after the owner agrees.
- **Test before saying done**: layout at phone, iPad and laptop sizes, portrait and landscape, with no sideways or up-and-down page scroll, measured and not guessed. Say plainly what could not be tested here (the installed iPhone app, Safari's own gestures) and ask for a check on the phone.
- **Neat and clean**: nothing may run off a panel or the screen, at any text length or width. Check the longest text (September, Wednesday) at 320px wide.

### Code

- Comment the code: a header on every file saying what it is for, and a short doc comment on each exported function, hook and component. Match the style of the surrounding code.
- Keep the calendar modular and exportable: everything it needs lives inside `src/photo-calendar/`, and other code imports it only through `src/photo-calendar/index.js`.
- All Write-With-Nature (WWN) glass code stays inside `src/photo-calendar/wwn-glass/`, imported only through its `index.js`. Local changes to the copied WWN files are marked `LOCAL CHANGE` and listed in that folder's README (today: the optional letter font family, and the date-tile highlight fading out over the flat body in `glass-alphabet/scene.ts`).
- **The glass draws only when something changed.** Scenes skip the upload and the draw on a frame where nothing new was set; a glass piece that changes its backdrop canvas or resizes its canvas must call `scene.invalidate(reason)`, and anything drawn over the wallpaper that the glass refracts must call `bumpContent(region)` (see `photoLayer.js`). Details in `src/photo-calendar/wwn-glass/README.md`. Check `glass frames drawn / skipped` on the diagnostics card: an idle page should draw nothing.
- Keep the typegpu packages pinned exactly: `typegpu` 0.12.4, `@typegpu/sdf` and `@typegpu/noise` 0.12.0, `unplugin-typegpu` 0.12.3. `typegpu` 0.12.6 renders the glass panel black, and `unplugin-typegpu` 0.12.4 demands 0.12.6, which breaks `npm ci`.
- **Updates reach an installed app without deleting it.** `public/sw.js` installs a new version in the background and lets it WAIT (only the first ever install activates at once); `src/pwa/register.js` notices it, `src/pwa/UpdatePrompt.jsx` shows a glass pill "New version available, tap to reload" above the bottom buttons, and the tap sends `SKIP_WAITING`, after which the page reloads once. Nothing from the old version is deleted until the tap, so a running page can still load its pieces. The app looks for a new version whenever it comes to the front, comes back online, and every 30 minutes; `sw.js` is registered with `updateViaCache: 'none'`, and the install and the page loads skip the browser's own 10 minute cache (GitHub Pages serves everything with `max-age=600`). The build time is on the diagnostics card (`__BUILD_TIME__`), so a phone's version can be checked. Tested with a production build served by `vite preview` (build one version, deploy the next underneath, watch the prompt appear and the tap reload); it cannot be tried in the dev server because the service worker only registers in production builds.
- PWA and hosting: the app builds with relative URLs (`base: './'`) so it works on a GitHub Pages project path. `public/sw.js` has placeholders that `vite.config.js` fills at build time; do not hard-code asset names in it.
- Imported photos live only in IndexedDB on the device (`src/photo-library/`). Never add code that uploads them. Dates come from the EXIF string as written (no timezone conversion); keep `reviveValues: false` and do not combine it with `pick` (exifr 7.1.3 throws). A change to how photos are stored needs an IndexedDB upgrade step so no update ever needs a wipe.

### Layout

- The calendar responds to its own width (container queries in `src/photo-calendar/styles/`), not the viewport. The day view is the exception: it is a portal, so it uses viewport media queries.
- **The document never scrolls**: `html`, `body` and `#root` are exactly the screen, `body` is fixed; `.stage` is the only scroll container and scrolls only when the content is genuinely taller than the screen. Every row (the gear, tile style button and Get your calendar) stays within the screen width. Scroll listeners use capture.
- **Date boxes are square** with small gaps (`--pc-gap`), sized by the panel width. **A phone on its side** (`compact.css`, `app.css`), where the height is all there is. The boxes are still squares there (`--pc-tile-ratio: 1` in `compact.css`; wider boxes, 1.7 and then 4:3, were tried to use the spare width but cropped upright phone photos too much), sized from the height left: the screen less the page padding (which grows with the iPhone's safe-area margins, the home indicator takes 21px), less 68px for the header, weekday row and panel padding, less the row gaps, split between the month's rows (`--pc-rows`), so a five-row month gets taller boxes than a six-row one. The panel is as wide as seven boxes and centred, which leaves wallpaper at the sides. **The gear, info and matte/glass buttons are not on the first screen in landscape:** they sit in a row below the calendar, and the page scrolls (about 100px, no scroll bar) to reach them; the calendar column is at least one full screenful, so the calendar is centred and the buttons start below the fold. The page-level scroll bar is hidden everywhere (`.stage`). Tested on every current iPhone landscape size (667x375 to 956x440) with emulated safe-area insets (`Emulation.setSafeAreaInsetsOverride`: left and right 47 to 62, bottom 21), for 4, 5 and 6-row months: nothing outside the usable area, and the settings menu fits once scrolled to.
- **Wrap, do not overflow**: rows on the calendar panel and the day sheet are `flex-wrap: wrap` (`.pc-head`, `.pc-title-row`, `.pc-detail-head`). When a month name or weekday is long or the panel is narrow, the arrows (and the day sheet's buttons) drop beneath on the right. Anything new on a panel must wrap or shrink (`min-width: 0`), not take a fixed width.
- **Get your calendar** (built, not pushed; branch `export-calendar`): a glass button at the right end of the bottom row (`src/GetCalendarButton.jsx`, with a lilac glow: `glow` on the item, `buttonGlow` in `wwn-glass/theme.js`, `glowBreath: false`, `litTint` and `glowStrength: 0` in its material: the glow is steady so the idle page still draws nothing, and there is no bloom around the letters, so the words look exactly like "info" and "flat"). It opens `src/photo-calendar/export/ExportPage.jsx` for the month on screen (`PhotoCalendar` reports it through `onViewChange`; `paused` stops its keys while the page is open). The page is plain, like the year view (no glass): the wallpaper, a sheet showing the month's calendar, the page-shape button, Back and Save. On a landscape page the boxes on the sheet are squares (as big as the page allows: seven across the full width, or smaller if six rows would not fit the height, with the grid centred and the title lined up with its left edge). An upright page keeps its own layout: seven boxes across the full width, a little taller than wide, starting right under the weekday labels. The sheet is one canvas drawn by `drawCalendarPage.js` from the numbers in `pageLayout.js`, at screen size for the preview and at full size for the file, so what is seen is what is saved. Months can be changed on the page: previous and next are just an arrow (no circle) at each side of the screen, vertically centred like the photo viewer's, with the month announced to screen readers only (the sheet already shows it); they give a subtle jelly wiggle when hovered or focused (about 3px of push and a few percent of stretch) and a light squash when pressed (`ec-wiggle` in `export.css`, off for reduced motion); the left and right keys and a swipe on the sheet work too; the choice for each day is remembered per month. The hint ("Tap a day to choose its photo") is at the top of the page (hidden on a phone on its side, where there is no room). The page-shape button and the shuffle button (crossing arrows, no text; shuffle has a rainbow gradient with a pure white symbol, greyed out when disabled) are in the bottom bar, between Back and Save. Shuffle picks a random photo for every day of the month that has more than one, never the one already showing; it is disabled in a month where no day has several. The page's shape is one button with no text, a phone drawn upright or on its side that turns when pressed (it shows the current shape), and the sheet starts in the screen's own shape. Tap a day with photos (invisible buttons over the sheet, keyboard reachable) to choose which of its photos is on the sheet, or "Leave blank" (at the left of the chooser, Cancel at the right) for none; the chooser is titled "Pick a photo for October 5". The sheet's canvas is made with `willReadFrequently: true`, because the drawing reads pixels back to pick the number's colour over a photo, and without it the browser switched text renderer partway and the same sheet drew its digits slightly differently from one redraw to the next. The first photo of each day is the default. Text is pure black or white from the wallpaper behind it. The four round buttons in the bottom bar (Back, page shape, shuffle, Save) wiggle gently when hovered or focused (a few degrees and about 6% of scale) and bounce when pressed (the `ec-pop` class that `pop` in `ExportPage.jsx` adds on click, so a tap on a phone, which has no hover, gets it too; it needs a higher priority than the hover rule, and both are off for reduced motion). Back and Save are small (36px) round buttons, darker red and lilac so their pure white symbols read cleanly, with a symbol instead of a word (Back: a return arrow that curves back, so it is not mistaken for the previous-month arrow; Save: the download tray, which becomes a turning arc while a file is being made; both have text labels for screen readers) in a bar along the bottom of the page, where a thumb reaches them (the month and its arrows are alone at the top; on a phone on its side they sit in the bottom corners, over the free space either side of the narrow sheet, so the sheet keeps its height). The Back button is a red pill in the same style (soft gradient, darker edge, glow, black text), so the two ends of the bar read as "leave" and "go on". Pressing Save (a lilac pill, the colour of the Get your calendar button, with black text) opens a small dialog asking how to save: **Picture (PNG)**, described as best for saving to the Photos app and for sharing (lossless, about 10 MB), or **Print-ready page (PDF)**, best for printing (a US Letter page at the right size, smaller file, saves to Files and not to Photos, the picture inside very slightly compressed). Both texts are meant to be accurate, so keep them in step with `saveImage.js` if either changes. The PDF is built without a library (`makePdf.js`): one page, 792x612 points (11x8.5 in; portrait 612x792), holding the finished page picture as a JPEG at quality 0.95 (about 1.5 MB), so its text is part of the picture, not live or vector text. Escape closes the dialog first. The PNG is the whole page at US Letter, about 400 dpi (landscape 4400x3400, portrait 3400x4400; if the browser cannot make a canvas that big, `canvasWorks` in `saveImage.js` falls back to 300 dpi, 3300x2550) and uses each day's full-size original, not the 720px preview the screen uses: `fullPhoto.js` decodes one original at a time (upright, rotation applied), crops it to its box and shrinks it in steps of at most half, then lets it go, so a month of 12 megapixel photos never sits in memory together (a day whose original cannot be read falls back to its preview); the status line counts them ("Preparing your photos, 5 of 12") and sends it through the share sheet on a phone (`navigator.share` with a file; if the browser wants a fresh tap, a "Save the picture" button appears) or downloads it on a laptop (`saveImage.js`). The bottom row wraps its right-hand pair (matte/glass and Get your calendar) to a second row on a screen under about 360px wide, and the calendar makes room for it (`--pc-extra-height` from `App.jsx`). 
**Still to decide about the export:** a vector PDF (live text and outlines, only the photos as pixels) for big prints, other paper sizes (US Letter now; A4 and others), whether to let the person pick a size, whether photos should be saved to Photos or Files directly, and extras (a title, a note per day, week start).
- **Photo count** ("2 photos this month", "5 photos this year"): a small italic line under the calendar panel, at its left (`PhotoCount.jsx`, colour from `usePageInk`), no longer in the header; hidden on a phone on its side. It shares its line (`.pc-under`) with the camera button at the right (see Camera button); that line's height (about 36px) is part of the 312px allowance in `--pc-tile-max` (`base.css`).
- **Camera button** (branch `camera`, not pushed): a glass tile with a drawn camera (`src/CameraButton.jsx`), under the calendar panel at the right, on the same line as the photo count (`underRight` prop of `PhotoCalendar`, `.pc-under`; on a phone on its side, where the count is hidden, it sits beside the panel's bottom right corner instead, see `compact.css`). Its dialog is portalled to `document.body`, because the calendar's containment would trap a fixed-position child. A photo taken with it is imported like any other (`addFiles` in `usePhotoLibrary`), so it lands on the day it was taken: the date in the photo's own metadata, or else the moment it came back (now). On a touch device (`(pointer: coarse)`) a press opens the in-page phone camera (`PhoneCamera.jsx`, `phone-camera.css`), drawn like the phone's own Camera app: the live picture fills the whole screen (the stream is asked for as 16:9 at 3840x2160, shown with `object-fit: cover`, and what is saved is cut to exactly what is shown, and to the digital zoom, by `captureFrame`), close at the top left, flash at the top right, a zoom pill above the shutter, and along the bottom, over the picture on a soft dark fade, the last photo taken, the big white shutter and flip front/back. It stays open after a shot so several can be taken, and closes with the close button or a tap on the last photo. It was chosen over the phone's own camera screen (a file picker with `capture`), whose \"PHOTO\" label, bar and controls a page cannot change. Sliding a finger down anywhere on the camera (not starting on a button) pulls it down like a sheet and closes it when pulled past 110px, or flicked (40px at over 0.6px/ms); otherwise it springs back; a second finger cancels the pull. Double-tapping the picture flips between front and back (two taps under 320ms and 40px apart, each a short press that stays put; taps on buttons and pinches do not count; ignored while a camera is restarting). Zoom stops are the real lenses where the phone shows them to the page (0.5 is the ultra wide, found by name in `cameraLenses.js`) and a digital 2x; pinching zooms digitally to 10x. The telephoto lens is not offered because a page cannot be told its strength. Zooming inside a lens is instant; flipping or changing lens restarts the camera (starting by `deviceId`), and the last frame stays blurred on screen meanwhile (`.pcam-snap`). Flash is Auto/On/Off (saved as `mycal.camFlash`): the front camera lights the screen white; the back camera uses the torch only where the browser allows it (`track.getCapabilities().torch`), which iPhone's browser does not, so the button is hidden there; Auto fires when the frame's average brightness is under 70/255. While it is open the page's background colour is set to black (and the theme colour), because the strip an installed iPhone app leaves below the page can only show that colour. Where that strip exists (`viewportDeficit() >= 20`) the picture ends in rounded bottom corners (`.pcam-curved`) with the black strip below, as in the phone's own camera; the strip cannot be painted over. The trade-offs: a page's camera gives no HDR, Night mode or telephoto, and 16:9 is about 8 megapixels against the native app's 12. The hidden `capture="environment"` input stays as the fallback (offered on the phone camera's error screen, and used when the browser has no `getUserMedia`). `useCameraStream.js` holds the stream and capture code shared by both in-page cameras. On a computer a press opens a small camera inside the page, drawn as a Polaroid (`CameraDialog.jsx`; its Flip button, in the top right corner level with Close, turns the picture left to right, for the preview and the saved photo alike, remembered as `mycal.camFlip`: the page never flips a laptop camera by itself, but some cameras and virtual camera software do; a white print tilted a little, the live picture uncropped so what is shown is what is saved, and today's date written in the thick strip underneath in Playfair Display italic, the app's own face, pure black like all text; a true handwriting font would have to be hosted with the app, as no fonts load from the network; the print is straight, and the window in it takes the camera's own shape (a portrait camera gives a tall print), so there are no black bars; little flowers, leaves, hearts and sparkles are drawn on the white frame as vector art (`CameraFlorals.jsx`: a bunch over each top corner, a sprig either side of the date, hearts under it on very narrow prints; they hide in steps as the print gets narrower, and taps go through them);
  the shutter, a round WWN glass tile (64px, with a white ring and a soft disc drawn over it, dimmed and inert until the camera is live), sits under the print, and the close button is in the top left corner of the screen (the print starts below it in a narrow window); `getUserMedia`, the back camera where there is a choice, switched off when the dialog closes; a message explains a blocked or missing camera). Camera files are named `camera-YYYY-MM-DD-HHMMSS.jpg` (a phone's "image.jpg" is renamed the same way so captures are never mistaken for each other) and count as dated. After a single photo the toast says which day it went to ("Added to 6 October"). The extra button makes the bottom row two lines on phones narrower than about 430px (the calendar makes room for it). Not tested on a real phone: the camera app handing the photo back, and iOS's permission prompts.
- **A + button next to the camera button** (`src/AddPhotosButton.jsx`; branch `guided-tour`, not pushed): a second way to add photos besides the gear menu's Import photos. It is the same glass tile as the camera button (WWN springs, the jelly), a drawn plus over it, sitting left of the camera on the line under the calendar panel (both go in the `underRight` slot, which is now a flex row; on a phone on its side they stack, + above the camera, beside the panel's bottom right corner). A press opens the photo picker (a hidden multiple-file input, opened inside the press as iOS needs) and the chosen photos go through `addFiles`, so the same toast reports them; it waits while an import is running. The empty-calendar hint now says "No photos yet. Tap the + to add some."
- **Dates carry their ordinal suffix (6th, 22nd) everywhere except on the day tiles.** `ordinal(n)` and `ordinalSuffix(n)` are in `lib/dates.js` (1st, 2nd, 3rd, 4th ... 11th, 12th, 13th ... 21st, 22nd, 23rd, 31st; exported from `photo-calendar/index.js`). They are used in the day sheet's heading ("12th October 2026"), the "Added to 6th October" message, the export page's chooser ("Pick a photo for October 12th"), and the spoken labels and tooltips. The numbers drawn on the date tiles (the glass and matte month tiles, and the boxes on the exported calendar picture) stay plain digits on purpose, so the tiles stay uncluttered; an attempt with small raised suffixes there was tried and taken out on request.
- **Header**: the year button sits beside the month name, with its digits on the month's baseline (`--pc-month-size`); the photo count is under the panel (see above). In year view the title is the year and the button shows the month it returns to.
- **Deleting photos from a day works like the iPhone Photos app** (`DayDetail.jsx`, `detail.css`; branch `day-delete`, not pushed): press and hold a photo (450ms, finger or mouse; a move over 10px is a scroll) and it is selected; every photo of the day then shows an empty circle bottom right, and a tap selects or deselects it (a selected one shrinks inside its box and its circle fills blue with a tick). The header's last line becomes "Select Items" or "N Photos Selected" and the day's arrows and close button become a plain Cancel; day swipes, the arrows and pinch-to-month are off while selecting. A lilac round Save button at the bottom left (the lilac of the export page's Save, a white tray arrow; `saveOriginals` in `photo-calendar/lib/saveOriginals.js`) hands over the selected photos at their original size: the stored original file (`file` on each photo from `usePhotoLibrary`, via `originalsOf(srcs)`, never the 720px preview or a resized copy, names and metadata kept). On a phone or tablet it opens the share sheet with the files (its "Save Image" puts them in Photos; a web page cannot write into Photos directly) and the call is made straight from the tap, as iOS requires; on a computer it downloads them one by one. The selection stays after saving. A round trash button at the bottom right of the sheet, styled like the red Back button of the Get your calendar page (red gradient, red glow, pure white symbol), is live once something is selected and opens a sheet that rises from the bottom: what happens in plain words (removed from this app, Photos library not affected), a red "Delete N Photos" and a Cancel. Keys: Delete or Backspace asks, Escape steps back (the question, then the selection, then the photo, then the day). Deleting shrinks the photos away, then `removePhotos(srcs)` in `usePhotoLibrary` deletes the records in one IndexedDB transaction (`deletePhotos` in `photo-store.js`) and trims the list in place (no reload, no flash); a day left with no photos closes. The calendar only offers this when the page passes `onDeletePhotos` to `PhotoCalendar`. A day tile cycles its photos with `usePhotoRotation`, whose remembered position is kept inside the day's photos (`index % count`): without that, deleting photos left the tile pointing past the end, so it drew nothing (for good, with one photo left) until a refresh. The thumbnails' pictures take no pointer events (`pointer-events: none`) so iOS's own press-and-hold menu for pictures (Share, Save to Photos, Copy, Copy Subject, Look Up) does not open over the hold; that menu still opens on the photo in the full-screen viewer. Check on a real iPhone that the menu stays away. Selecting starts only by press and hold (there is no keyboard way in yet).
- **Previous and next are plain chevrons at the sides of the screen, on every view** (`SideArrows.jsx`, `styles/arrows.css`; branch `side-arrows`, not pushed): no circle, drawn in the page's ink (pure black or white), `position: fixed` at the screen's left and right edges, level with its middle, with a jelly wiggle on hover, focus and press. The month and year panels (stepping a month or a year; rendered in a portal on `<body>` because the calendar's `container-type` would trap a fixed child), the day sheet (previous or next day with photos; dimmed with no wiggle when there is none; not shown while selecting photos) and the calendar-export page all use the one component. The glass `<` `>` buttons are gone from the month header and the day sheet's header. Panels keep clear of them: `--pc-arrow-room` (56px at each side, 28px on a phone) is taken off the calendar's width (`.pc-root`, base.css and compact.css) and added to the day overlay's side padding (detail.css), so date boxes are about 10% smaller across on a phone than before. While a day or the export page is open the calendar's own arrows fade out with the rest of the page (`.pc-arrows-main`). Keyboard arrows, swipes and trackpad swipes are unchanged. **The arrows do not stay on screen** (`hooks/useTimedVisible.js`): they show for 5 seconds when the app opens, then fade away (.5s) so they take no room in the picture, and come back for 3 seconds whenever the view changes (a swipe, a key, an arrow, the year button), because the hook watches the month, year and mode (calendar), the day (day sheet, 3 seconds on opening too) or the month (export page, 3 seconds on opening). A pointer reaching the spot of a hidden arrow, or a focus on it, brings it back first (so a mouse click still steps); a touch on a hidden arrow only brings it back and the next tap steps, so a stray tap at the screen's edge cannot change the month. Hidden arrows are still in the page (keyboard focus reveals them).
- **Guided tour** (`src/tour/`; branch `guided-tour`, not pushed): twelve steps with few words and the app doing the showing, in the order a new person meets it: the month, the year (pinch or the year button), moving around (swipe and the side arrows), opening a day (a tap is shown on today's tile, then the day opens), a photo full screen (a tap, then it fills the screen), Get your calendar (a tap on the button, then the real export page opens), choosing a photo (a tap on today's day, then the chooser opens, a tap on the second photo, then it is chosen and shows on the day), the page's shape, shuffle and save buttons (a tap on each in turn), adding photos (a tap on the +, then the gear menu opens with a line saying it adds photos too), select / save / delete (a press and hold, then the photos in selecting mode with Save and the trash), a privacy line, the camera button.
